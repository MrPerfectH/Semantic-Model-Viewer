## Parser output

`TMDLParser.parseTMDL(files)` and `parseBIM(json)` add:

```js
model.powerQuery = {
  version: 1,
  nodes: [{
    id: JSON.stringify([kind, table || '', name]),
    kind: 'partition' | 'expression',
    table: 'Table name' | null,
    name: 'Partition or expression name',
    type: 'm' | 'calculated' | 'query' | 'unknown', // source.type / expression.kind
    code: 'Decoded exact M expression' | null,
    state: 'available' | 'missing' | 'non-m',
    classification: 'query' | 'parameter' | 'function' | 'declared non-M kind',
    basis: 'inferred from syntax' | 'M metadata marker (not evaluated)' | 'declared kind'
  }],
  warnings: ['Metadata extraction limitations/errors']
};
```

IDs encode object identity, independent of file order. Duplicate object identities
are not silently disambiguated; analyzers must treat duplicate names/multiple table
partitions as ambiguous. Shared expressions retain their own names. A table query
reference is resolved by table name, not partition name, with explicit uncertainty
when multiple partitions exist. Classification is a UI hint, never proof of M type
or evaluation behavior. Parameter markers and function signatures are syntactic
inferences; `basis` preserves that distinction. Missing partition sources have
`type: 'unknown'`, `state: 'missing'`, `code: null`.

Supported metadata: TMDL `partition … = m` / `source =`, and top-level `expression
… =`; BIM `model.tables[].partitions[].source.{type,expression}` and
`model.expressions[].{name,kind,expression}`. BIM string text is untouched; expression
arrays join with LF. TMDL removes structural indentation according to expression
boundaries; fences use the closing fence indentation and preserve trailing blanks,
whitespace and CRLF. Ordinary unfenced TMDL removes trailing blanks/whitespace under
TMDL rules. Existing parser limitations still apply to the analytical model itself;
this is not a full TOM/TMDL deserializer. Refresh-policy M, mashup binary/ZIP content,
PBIX/PBIT, connector credentials and live service metadata are not inspected.
Pre-generated viewer JSON and shared snapshots may have no Power Query metadata.

## UI extension hooks

`PowerQuery.open(app, tableName?)` opens the inspector. `PowerQuery.close(app)`
removes it on model replacement. Table and partition choices remain while navigating
shared code. UI uses text nodes for imported code; no raw HTML injection.

When present, each module is called after the code panel renders:

```js
window.PowerQueryDependencies.render(host, context);
window.PowerQueryLineage.render(host, context);
// context = { app, metadata, selected, table, partitionId, openCode }
// selected is a metadata node; partitionId is the selected table partition's ID.
// openCode(nodeId) opens any partition/shared expression in the same inspector.
```

Each hook gets its own empty `section`. Do not mutate `metadata` or run M. Own
listeners within `host`; do not retain global listeners/runtime state across model
replacement. Cache only with model/metadata identity; model changes create a new
inspector. Code navigation replaces hook hosts, so graph expansion state should live
in a model/partition-scoped module state. The integration owner will register new
script/CSS assets in `index.html` and the snapshot runtime allowlist. Worker modules
must be optional so #34/#35 works before dependent slices arrive.

`PowerQuery.tokens(code)` exists only for syntax highlighting. It is not a semantic
parser and is not a prerequisite for #36; the analyzer owns its scope-aware lexer
and parser. Do not infer certainty from the highlighting lexer.

## Export and safety boundary

`Snapshots.modelData(model)` uses its existing analytical allowlist and excludes
`powerQuery`, raw M, endpoints and other unknown metadata. No opt-in export of M is
introduced. Adding runtime JS/CSS to offline snapshots does not add model M content.
No M execution, source data reads or source-model edits are authorized.
