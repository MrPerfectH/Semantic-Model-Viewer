# Relationship and DAX diagnostics

Browser TMDL/BIM imports and the Python generator retain each valid relationship identity, including parallel relationships with identical endpoints. Missing table or incomplete endpoint records are omitted with a `relationshipDiagnostics` record: total examined, accepted, rejected, and named reasons. Browser import preview displays those counts and expandable reasons; Reference retains the omission notice after adoption and in exported snapshots. Previously exported models that already dropped records cannot recover evidence that was never saved.

The Node CLI remains deliberately strict: any rejected relationship prevents loading/export and reports accepted/rejected counts and reasons. Existing output is not replaced. Counts cover the parser's supported model relationships; BIM autogenerated local-date relationships excluded together with their unsupported tables are outside that set. Validation here does not prove DAX correctness or runtime filter behavior, nor does it validate that every named endpoint column exists.

App preparation also records dangling tables in legacy viewer JSON. Repeated preparation preserves prior omission evidence without counting it twice. Snapshots include only diagnostic counts and name/reason fields.

Quoted missing whole-table references such as `COUNTROWS('Gone')` remain unresolved static evidence. Reference shows the unresolved identifier; Measures uses the same resolver and shows its unresolved count. Known tables still resolve, while functions, comments, strings and declared unquoted variables are excluded. Unquoted unknown bare tokens remain conservative because they can be language syntax; this is not a complete DAX parser.

Verification: app/parser/CLI/snapshot/Reference tests plus Python/browser relationship parity and the mocked VS Code protocol test. Real browser import preview, adoption, reload and Reference dependency evidence were checked on the development build. Actual packaged VS Code execution remains separate.
